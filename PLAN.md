# Plan: better quality news

Goal: fewer junk stories, fewer missed ones. The paper began with one reader (the author); since 24 Oct it is written for other Salesforce practitioners too, and new readers are expected to come from search.
Budget: a few dollars a month at most; new features under about $0.25 a month unless optional.

  - **Source: the release notes only.** Entries come from each release edition's enforced updates, which already look ahead (Winter '27's notes list 23 items reaching into Summer '27). - [ ] 8. **Reader feedback.** Planned 25 Oct; 8a built the same day. A preview of every screen is at `/preview/feedback/` under `npm run dev` (it is never built into the site). Now that the paper has other readers, they can say which stories were worth it and where one is wrong, and the editor can act on it.
  - **What the reader sees.** One line at the foot of every story: "Useful? Yes No" and, at the end of the line, "Report an error". Yes or No counts the moment it is pressed. No then offers four reasons (not about Salesforce, old news, not for my role, not worth the read), all optional. Report an error asks where the mistake is (headline, summary, diagram, link or source, something else) and takes an optional note of up to 500 characters. Everything opens inside the story's own box, never a pop-up, in the paper's type, square, in light and dark. The browser remembers the answer, so a story already answered says "Thanks" on the next visit.
  - **Anonymous, no sign-in.** The paper has no accounts and should not get them for this; few readers would sign in to say one word. No cookies. A vote counts once per story per browser (remembered in the browser) and once per address a day (the address is hashed with a salt that changes daily, then thrown away).
  - **Private reports, public corrections.** What readers send is read by the editor only, and counts are not shown on the page ("12 found this useful" says little on a day-old story and invites gaming). When a report is right, the story is fixed and prints a correction under its text ("Correction, 25 Oct: an earlier version gave the limit as 100 records. It is 50."), as a newspaper does. Corrections also show search engines the paper is looked after.
  - **Where it goes: a small Cloudflare Worker and D1.** The site is already served from `dist` by Wrangler on Cloudflare. A Worker script in front of the same static files answers `POST /api/feedback` and writes one row to a D1 table (story id, vote or report, reason, part, note, day, hashed address). Within the free tier by a wide margin, so $0. Turned down: GitHub issues (notes would be public in a public repository, the Worker would hold a GitHub token, and spam would land in the repo), a form service (another company holding readers' notes), Workers KV (counting is awkward).
  - **Spam.** A hidden field that only programs fill; the Worker refuses story ids that are not in the paper (it reads `search.json` from its own files); at most 20 votes and 3 reports an address a day; notes cut to 500 characters, links removed. Cloudflare Turnstile on reports only, loaded when the report form opens, so reading the paper still asks nothing of anyone else's servers.
  - **How the editor reviews it.** `npm run reader-feedback` pulls new rows from D1 into `data/reader-feedback.jsonl`, which is kept out of git because the repository is public. The Logs page, under `npm run dev`, gets a Readers section: each story with its Yes and No counts and reasons, and each report with its note and three buttons: Print a correction, Redraw the diagram, Dismiss. A story with more No than Yes (and at least 3) offers "Mark junk", which adds it to the hand-kept feedback log (step 1), so replay and tuning (2a, 2c) learn from it. Readers' No never reaches the scoring by itself: the editor decides, so a few readers cannot steer the paper. The Stats page shows only totals: votes a week and the share that were useful, by section.
  - **Summaries and diagrams.** Reports name the part that is wrong, so the fix goes to the right place. Headline or summary: edit the story's Markdown, or `npm run revise -- --story <id>` (a new option) with the reader's note given to the model as a hint. Diagram: `npm run figures -- --story <id>` draws it again, or the figure is taken off. Either way the story's front matter gets `corrections: [{ date, text }]`, which is printed. Reports are counted by the model that wrote the story, so a pattern in the AI's mistakes shows on the Stats page.
